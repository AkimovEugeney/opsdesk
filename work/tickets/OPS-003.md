## Business value

Старший оператор может назначить или переназначить ответственного за активное клиентское обращение, чтобы работа не оставалась без владельца.

## Context

В системе есть роли оператора и клиента. Identity prerequisite is complete: the API can resolve the authenticated current user from the server-side session. A senior operator is an `OPERATOR` whose per-user permissions list contains `canManageAppeals`; the list may be empty and OPS-003 adds no other permission.

Authentication and the trusted current-user source are implemented. The permission representation and protected endpoint are also present in code. This ticket still needs observed contract behavior and a correct concurrent-close failure mapping; code presence alone does not close it.

## Visible requirements

- `PATCH /appeals/:id/owner` accepts a positive integer `ownerId` in the JSON body and returns `200` with `id`, `status`, `ownerId` and `updatedAt` after a successful assignment.
- Старший оператор может назначить себя или другого оператора ответственным за новое обращение. После назначения статус обращения становится `IN_PROGRESS`.
- Старший оператор может переназначить ответственного для обращения со статусом `IN_PROGRESS`.
- При переназначении обновляется дата изменения обращения.
- Закрытое обращение нельзя изменять.
- Клиент не может менять статус или ответственного обращения.

## Acceptance criteria

- Для нового обращения назначается ответственный, а статус становится `IN_PROGRESS`.
- Для обращения в работе ответственный меняется на выбранного оператора, а дата изменения обновляется.
- Владелец и статус сохраняются после запроса.
- Попытка изменить закрытое обращение завершается ошибкой.
- Пользователь без права управления обращениями не может выполнить изменение.
- Для некорректного идентификатора или выбранного клиента API возвращает `400`; для отсутствующего обращения или исполнителя — `404`; для закрытого обращения — `409`; статусы авторизации записаны в requirements log.
