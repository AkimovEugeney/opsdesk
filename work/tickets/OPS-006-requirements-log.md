| 2026-09-22 | Industry practice for session timeouts (checked against authoritative sources) | OWASP Session Management Cheat Sheet: implement both an idle timeout and an absolute timeout; common idle ranges are 2–5 minutes for high-value applications and 15–30 minutes for low-risk ones; for an application used by an office worker for a full day an absolute timeout of 4–8 hours is appropriate; an absolute timeout is required regardless of activity. | 2026-09-22 | Why consumer products appear to have a permanent session | They do not keep one long-lived credential: the visible behaviour is a chain of a short access credential and a longer refresh credential that the client silently exchanges, so the user is never interrupted. Publicly documented examples: VK ID issues access tokens of about 60 minutes with a refresh token of about 180 days, while VK service and community tokens are documented as having no expiry at all (historically the `offline` scope); X issues a refresh token with `offline.access` that does not expire on a schedule. Consumer products can afford this because account risk is handled elsewhere — payment and profile changes require step-up verification (SMS, push, biometrics), sessions are device-bound with a visible device list and revocation, and an unnecessary logout costs the business a user. This is exactly the context-dependent trade-off OWASP describes, and NIST AAL1 (30 days) shows a long session is not automatically out of standard. Practical consequence for OpsDesk: a long session is achieved by adding a rotating refresh credential with reuse detection, not by setting a one-year cookie, and that is a separate ticket outside this one's single-concept limit. | https://id.vk.ru/about/business/go/docs/ru/vkid/latest/oauth/oauth-vkontakte/authcode-flow-community; https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html; https://pages.nist.gov/800-63-4/sp800-63b.html |
| 2026-09-22 | Correction: a long-lived browser session with `HttpOnly` is not automatically a mistake | The mentor's earlier statement was too absolute and is refined here. `HttpOnly` + `Secure` + `SameSite` do close the vector of page scripts reading the credential, so a long-lived refresh in a browser cookie is a conscious trade-off rather than a design error, and business tools do exactly that. What remains after the flags: (1) `HttpOnly` prevents reading but not use — while an XSS is live, requests are still sent with the user's cookie, so the attacker acts through the browser (OWASP notes the XSS-plus-CSRF combination); (2) browser extensions holding the `cookies` permission plus host permissions can read `HttpOnly` cookies — documented in the Chromium extension design document; (3) endpoint infostealer malware reads the whole browser cookie store from disk, bypassing MFA entirely — the dominant session-hijack vector in 2025–2026 vendor reporting, with one infection typically yielding far more cookies than passwords, and no cookie flag helps there; (4) a persistent cookie outlives a closed browser, so a shared, lost or stolen computer keeps the session open; (5) if front end and API live on different sites, `SameSite=None` is required and CSRF protection must be built explicitly. Mobile apps face the same chain with stronger storage (OS keychain, app sandbox, device lock, biometrics), which is why the identical refresh credential is safer there. Mitigations used with long browser sessions: rotation with reuse detection, absolute cap, inactivity expiry in days, device/session list with revoke-all, step-up confirmation for sensitive actions, short access credential held in memory only, and anomaly monitoring. | Chromium extension Cookies API design document; OWASP Session Management Cheat Sheet; industry infostealer reporting (vendor sources, not standards) |
