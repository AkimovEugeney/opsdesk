## Business value

Оператор работает от собственного имени: система подтверждает учётные данные при входе и знает, кто выполняет запрос. Без доверенного текущего пользователя нельзя безопасно разрешить изменение обращения (OPS-003), поэтому это следующий шаг продукта, а не технический долг.

## Context

Сейчас API не различает пользователей: любой запрос обрабатывается анонимно, и данные, которые прислал клиент, нельзя использовать как доказательство личности. Это зафиксировано как причина блокировки [OPS-003](OPS-003.md) 2026-09-08. Пользователи и обращения уже есть в базе; учётных данных у пользователей пока нет.

The ticket deliberately covers authentication only. Permission enforcement (who may change what) is the next slice and belongs to the task that unblocks OPS-003.

## Visible requirements

- Пользователь входит, предъявляя свои учётные данные; при верных данных API подтверждает вход и выдаёт признак сессии, при неверных — отвечает `401` без деталей о том, что именно неверно.
- Пароль не хранится в открытом виде и не возвращается в ответах; значение пароля не попадает в логи.
- Запрос с действительным признаком сессии обрабатывается от имени этого пользователя; запрос без него или с испорченным, просроченным признаком не считается запросом от чьего-либо имени.
- Клиент не может назвать себя в запросе и тем самым получить чужую личность.
- Существующее поведение `GET /appeals` и `GET /appeals/:id` не меняется: этот тикет не вводит правила доступа и не закрывает чтение.
- Контракт входа зафиксирован в requirements log: вход по `email` и паролю через `POST /auth/login`; отпечаток пароля в `User.passwordHash`; серверная сессия в таблице `Session` с непрозрачным идентификатором в httpOnly cookie; текущий пользователь читается через `GET /auth/me`.
- Идентификатор сессии генерирует сервер криптостойким генератором случайных чисел, не менее 64 бит энтропии, и его значение ничего не значит для клиента: всё, что он обозначает, хранится на сервере.
- Cookie сессии выставляется с `HttpOnly` и явным `SameSite`; признак `Secure` включён для окружений по https и снят только для локальной разработки по http.
- Срок сессии ограничен двумя значениями: максимум с момента входа и предел бездействия. Оба значения задаются в одном месте, чтобы сценарии проверки можно было ускорить.
- Значение идентификатора сессии не попадает в логи и ответы API.

## Acceptance criteria

- Вход с верными учётными данными существующего пользователя завершается успехом; вход с неверным паролем и вход с несуществующим пользователем дают одинаковый `401`.
- `GET /auth/me` с действительной cookie возвращает того же пользователя; без cookie, с изменённым или просроченным идентификатором отвечает `401`.
- После разового обновления существующей базы все три существующих пользователя могут войти; новые значения задаются как данные разработки.
- В базе нет столбца или строки с открытым паролем; пароль не встречается в логах и ответах API.
- Поведение списка и карточки обращения не изменилось.
- Ученик сам выбирает конкретные проверочные сценарии на основе требований.

## Risks

- A stolen or forged credential must not become a way to act as another user; the invariant is that a request is attributed to a person only when it carries a valid credential issued by the API, and never when the client names itself. Verification: the denied paths (wrong password, unknown user, altered or expired proof) plus a review of the trust boundary.
- The same rejection must not reveal whether an account exists, and passwords must not reach logs, error messages or the database in clear text.
- Existing users have no credentials; if the first credential source is not defined, the feature would be testable only on new rows — the learner decides this in the design.
- Open-data risk: a session proof that is valid forever would keep a leaked credential usable; the learner states its validity and what happens when it is absent or expired.
- Session-specific risk: a stolen cookie acts as the person until the session row is removed or expires. The invariant is that only the server-side session record links a request to a user, so removing that record ends access immediately; the check is a request with a deleted or expired session plus a review of where the cookie is read.
