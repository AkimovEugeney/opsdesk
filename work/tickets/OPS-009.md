## Business value

Недопустимый идентификатор нового ответственного останавливается на границе HTTP-ввода, поэтому защищённое назначение не передаёт неверные данные в business/service layer.

## Context

`PATCH /appeals/:id/owner` currently validates `body.ownerId` with a controller `if`. Its route `:id` already has `ParseIntPipe` and a range check. OPS-003 explicitly deferred DTO validation so authorization remained its only major new mechanism. No `class-validator`, `class-transformer` or `ValidationPipe` is currently configured in the API.

## Visible requirements

- Only `body.ownerId` for `PATCH /appeals/:id/owner` receives DTO-based local validation.
- A JSON number that is a positive signed 32-bit integer proceeds to the existing service.
- A string numeric value, fractional number, zero/negative number, and number above `2147483647` receive `400` before authorization/state/persistence behavior.

## Acceptance criteria

- The existing manual `ownerId` validation is replaced rather than duplicated.
- `{ "ownerId": 7 }` reaches the existing protected-write flow unchanged.
- `{ "ownerId": "7" }`, `{ "ownerId": 1.5 }`, `{ "ownerId": 0 }`, and `{ "ownerId": 2147483648 }` return `400`.
- Existing `:id` validation, login behavior, permissions and response contract remain unchanged.
- API build and the existing service test command pass.

- A global pipe could change unrelated login and endpoint behavior. The invariant is that only `PATCH /appeals/:id/owner` changes validation behavior; validation evidence includes the protected-write matrix plus unchanged excluded endpoints.
- Automatic type transformation could widen the established contract by accepting string `"7"`. The invariant is that only a JSON number is valid; the regression test rejects the string payload.
