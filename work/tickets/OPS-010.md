## Business value

An operator can finish in-progress customer work with a recorded outcome. A closed appeal preserves that outcome for later review instead of losing the reason the work ended.

## Visible requirements

- Only the current assigned owner, who must be an operator, may close the appeal and record its outcome. `CAN_MANAGE_APPEALS` remains an assignment permission, not a closure permission.
- Only an `IN_PROGRESS` appeal may be closed.
- The request carries a nonblank outcome after trimming; its maximum length is 2000 characters.
- A successful close returns the closed state and recorded outcome.

## Acceptance criteria

- The API accepts one close request for an existing in-progress appeal and atomically persists `status: CLOSED`, `outcome`, and `closedAt`.
- A response returns `200` with `id`, `status`, `outcome`, `closedAt`, and `updatedAt`.
- Missing session returns `401`; a client role returns `403` before appeal lookup; missing appeal returns `404`; a different authenticated operator returns `403`; owner with `NEW`/`CLOSED` state or a concurrent state/owner change returns `409`.
- `NEW`, already closed, and concurrent close attempts return `409` with no partial state change.
- Missing, blank, non-string or overlong outcome returns `400`.
- Existing owner assignment, list/detail behavior, permission model, and public user projection stay unchanged.
- Migration, generated Prisma client, API build, relevant automated tests and a focused runtime validation matrix pass.

## Learning purpose

- Primary: design a protected state transition whose outcome and state must persist together.
- Practised: trusted current-user context, narrow error mapping and public input boundaries.
- Lookup-only: Prisma migration syntax, generated client surface and exact DTO decorators.

## Readiness

- `AppealStatus.CLOSED`, nullable `closedAt`, trusted current user, and a status-filtered protected update already exist.
- The schema has no `outcome`, close endpoint, close repository method, or close behavior tests.
- `outcome TEXT NULL` is applied to the local database. Actual rows before the decision: 2 `NEW`, 1 `IN_PROGRESS`, 1 `CLOSED`; the historical closed row has no outcome and remains `null` rather than receiving invented data.

## Intentionally excluded

- New permissions/roles, a global validation pipe, notifications, update history, frontend UI, customer-facing projection changes, and general status editing.
- Backfilling a fabricated historical outcome is excluded; legacy closed rows can retain `outcome: null`.

## Risks

- A read-then-unconditional-write implementation could let a concurrent request overwrite a closed record or leave outcome/state inconsistent. The invariant is that successful close sets outcome, `CLOSED`, and `closedAt` in one conditional persistence operation.
- Assigning one permission to closure could let a manager record an outcome they did not perform. The invariant is that only the current owner-operator can complete the work; a client is refused before lookup, while an operator is checked against the retrieved owner relation before state evaluation.
