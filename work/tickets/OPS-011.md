## Business value

An operator sees the active work queue in the browser, in Russian, instead of reading raw API answers. This is the first product view connected to the already verified read API.

## Context

- `apps/web` is a Next.js 16 / React 19 / TypeScript App Router project created in OPS-008. `src/app/page.tsx` is still a static server component with placeholder text; `layout.tsx` already carries the Russian title; `page.module.scss` exists but is unused.
- `GET /appeals` is public and already returns active appeals (`NEW`, `IN_PROGRESS`) with `id`, `status`, `title`, `description`, `createdAt`, `clientName`, `ownerName`.
- The API currently has no CORS configuration (`apps/api/src/main.ts` registers `cookieParser` only), so the browser cannot read `http://localhost:3000` from the web origin without an explicit decision.
- Local data: three active appeals (`NEW`, `NEW`, `IN_PROGRESS`) and one `CLOSED` appeal that the active filter must keep out of the list.

## Visible requirements

- The page shows the active appeals returned by `GET /appeals`.
- Each entry shows the title, the status and the client; the assigned owner is shown when one exists.
- Three distinct outcomes are visible to the user: data is loading, the request failed, or the queue is empty.
- User-facing text stays Russian.
- `CLOSED` appeals are not part of the queue.

## Acceptance criteria

- Opening the web page in a browser shows the active appeals as reported by the API — with the current local data, three entries and no closed one.
- An unreachable or failing API shows the error state instead of an empty list; a slow answer shows the loading state before data arrives; an empty API result shows the empty state.
- `npm run build` and `npm run lint` pass in `apps/web`.
- If the chosen fetch boundary requires an API change, that change is limited to the agreed boundary; otherwise `apps/api` and its contract stay untouched.

## Secondary skills

## Readiness

- Existing: web app scaffold, Russian layout metadata, public read endpoint with a verified response shape, and a verified active-state filter.
- Missing: any data access from the web app; an API-side origin policy if the browser calls the API directly.
- Learner prerequisite evidence: React `useState` applied and explained in OPS-008; no prior evidence for cross-origin browser calls, so the boundary decision is mentor-recommended and learner-accepted rather than learner-invented.

## Deferral (2026-10-03)

- The learner rejected the ticket at refinement: an internal operator queue must not be the first browser screen, because today it would be an anonymous view of a public endpoint while the product's screens are authenticated. The learner asked to deepen backend work first and to return to the frontend in roughly four sessions.
- Consequence: the read view is not started, and the fetch-boundary decision stays open. It is resumed once the authorization screen (login/session UI) exists, so the queue is shown to an authenticated operator.
- Recorded rather than deleted: the ticket and its requirements log preserve the drafted contract and the undecided boundary question.

## Intentionally excluded

- Login/session UI, assignment and close actions in the browser, search/filter UI, styling system, pagination, date formatting beyond what is needed to render, tests of the web view.

## Risks

- An API origin policy that allows every origin (or a wildcard together with credentials) would remove the boundary it is meant to create; the invariant is an explicit allowlist of the web origin, and no credentials unless an authenticated flow needs them.
- A UI that cannot distinguish "request failed" from "no data" would report an outage as an empty queue; the invariant is three separately observable states, and the verification must include an unreachable-API case.
