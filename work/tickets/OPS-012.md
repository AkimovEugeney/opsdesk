## Business value

An operator can end their own session instead of waiting for a timeout, so a shared terminal does not keep a usable session alive. The login screen that follows needs this action before it is worth building.

## Context

- `POST /auth/login` sets an HttpOnly cookie `sid` whose `maxAge` is the absolute session lifetime (8 h); `GET /auth/me` resolves the current user from that cookie.
- `AuthService.getCurrentUser` rejects a missing, unknown or expired session with `401`, but deletes nothing.
- Nothing in `apps/api/src` terminates a session: no `logout` route, no `clearCookie` call and no `Session` deletion exist today. Sessions end only through the idle/absolute comparison in `auth/session-timeout.ts`.

## Visible requirements

- After the request, the session identifier that was presented can no longer be used.
- The response makes the browser drop its session cookie.
- A logout request without a usable session still leaves the caller without an active session.
- A database failure is never reported as a successful logout.
- Other sessions of the same user are unaffected.

## Acceptance criteria

- Reusing the same cookie after logout on `GET /auth/me` (and any protected route) returns `401`.
- The session row with that identifier is gone, while another session of the same user still exists.
- The response carries a `Set-Cookie` that expires the session cookie for the same path the login flow used.
- No cookie, an unknown value and an already-ended value all produce the same success status and expire the cookie.
- A simulated persistence failure produces a server error, not the success status.
- Login, `/auth/me`, the timeout rules and the appeals flows are unchanged; `npm run build` and `npm test` pass.

## Readiness

- Existing: `Session` model (`id`, `userId`, `lastActivityAt`), an `AuthService` that already looks a session up by identifier, cookie name/attribute constants, and the login flow that sets the cookie.

## Intentionally excluded

- Ending every session of a user, revoking sessions on credential change, a cleanup job for expired rows, CSRF hardening beyond the existing `sameSite: 'lax'`, audit/history records, and any frontend work.

## Settled design (2026-10-03)

- New route on the existing auth controller: `POST /auth/logout`, success status `204`, set explicitly because Nest defaults a successful `POST` handler to `201`.
- Order of operations: delete the presented session identifier first, then expire the cookie; a persistence failure returns a server error and the cookie is not expired.
- No read and no expiry check before the delete: an unknown or expired row already satisfies the postcondition.
- Persistence: a count-returning bulk delete by identifier (`deleteMany`), because a single-row delete raises `P2025` on an absent row while absence is the desired result. The count is not part of the response.
- Cookie: expired for the same path the login flow used; an HttpOnly cookie can only be removed by the server, so this is the only way a client leaves the authenticated state.
- Service: the auth module has no repository layer and `AuthService` already uses `PrismaService` directly, so the terminating method follows that shape.
- Tests: a dedicated auth service test file plus an explicit two-file test script, because the current script runs only `test/appeals.service.test.ts`.

## Risks

- Clearing only the browser cookie without removing the stored row would leave a session usable by anyone who captured the value; the invariant is server-side invalidation, not a browser-side deletion.
- Reporting a persistence failure as a successful logout would tell the user the session ended while it is still live; the success status is returned only after the row is gone or was already absent.

## Validation and review

- Observed build: `npm run build` passes after the final edit.
- Observed startup: the running API mapped `POST /auth/logout` alongside the existing `POST /auth/login`, `GET /auth/me` and appeals routes.
- Observed runtime matrix, run against two temporary sessions for an existing operator and cleaned up afterwards (session count 22 → 24 → 22, verified):
  - `GET /auth/me` with a valid session returned `200` before logout, for both temporary sessions.
  - `POST /auth/logout` with that cookie returned `204` and `Set-Cookie: sid=; Path=/; Expires=Thu, 01 Jan 1970 00:00:00 GMT`.
  - Replaying the same cookie on `GET /auth/me` after logout returned `401`, and the session row was gone (`count = 0`).
  - The second temporary session still returned `200`, so logout ended only the presented identifier.
  - `POST /auth/logout` with no cookie and with an unknown value both returned `204` with the same expiring `Set-Cookie`, confirming the idempotent decision.
  - The `204` also confirms at runtime that `@HttpCode` and `@Res({ passthrough: true })` coexist as described: the framework still applied the status while the handler wrote only the header.
- Tests: not added — the learner declined the auth service test file on 2026-10-03 and prefers product work. `npm test` stays green (appeals suite only). Durable automated coverage for logout remains open work.
- Review format: independent review required. This change alters a session boundary, which `docs/team/code-review.md` lists as a separate-review candidate (wrong-actor or stale-session scenario); a separate reviewer receives the ticket and the changed set, and the verdict is recorded here.
- Review verdict (independent, separate chat): PASS with no blocking findings. The reviewer confirmed the route is a state-changing `POST` with `204`, that the delete is a count-returning bulk delete by the presented identifier with no prior read, that the cookie is expired only after the call returns, and that no global filter or interceptor can swallow the failure.
- Observed failure path (closes the reviewer's material open risk): a second API instance started with an unreachable `DATABASE_URL` answered `POST /auth/logout` with `500 {"statusCode":500,"message":"Internal server error"}` and **no** `Set-Cookie`, while the log showed the genuine driver error (`P1001`, `DatabaseNotReachable`, model `Session`). The control case on the healthy instance answered `204` with the expiring cookie. No database data was touched by this check.
- Reviewer suggestions (non-blocking, not applied): drop the leading slash in `@Post('/logout')` for consistency with the neighbouring routes; match the file's spacing in the `deleteMany` call; pass the same cookie attributes `login` sets; remove the leftover scratch file `apps/api/src/_probe_cookie.ts` in a separate task.
- Evidence nuance (not a defect): the "already-ended" case was observed as a deleted identifier, not as a row that still exists but has passed the idle/absolute timeout; both identifiers are equally absent for the delete, and the timeout comparison itself was not re-observed in this ticket.
- Understanding check: passed. Asked what the API answers when the store is unavailable, what happens to the browser cookie and why; the learner answered that the request fails before the cookie clearing and a `500` is returned. Both parts are correct. The one addition: because the clearing never ran, the browser keeps its cookie and the session stays live, so the client must not be told it logged out — the delete-before-clear order is what keeps the success status honest. The explanation follows a rule supplied earlier in the session, so the ledger records it as assisted recognition rather than independent mastery.
- Acceptance coverage: every criterion is observed.
- Observed protected-route reuse: with one temporary session for the operator, `GET /auth/me` returned `200`; `POST /auth/logout` returned `204`; then both `PATCH /appeals/3/close` and `PATCH /appeals/3/owner` answered `401 {"message":"Session not found","error":"Unauthorized","statusCode":401}` with the ended cookie. The appeal row was identical before and after (`IN_PROGRESS`, null `outcome`, null `closedAt`, owner 3), the session row was gone, and the count returned to 22.
