## Business value

A client can file a new appeal instead of depending on seeded rows, so the `CLIENT` role finally has a product action of its own. It is also the first write whose author must come from the session rather than the request body.

## Context

- `apps/api` exposes read flows, owner assignment and close. There is no create endpoint, so a `CLIENT` can authenticate and then do nothing.
- The `Appeal` model requires `clientId`, takes `status` as an enum, and leaves `ownerId`, `outcome` and `closedAt` nullable.
- The learner implemented the endpoint directly, before a contract existed; the requirements below were recorded on 2026-10-03 **after** the code was written. The implementation is therefore checked against these rules, and any divergence is a defect to fix, not an accepted design choice.

## Visible requirements

- Only an authenticated client may create an appeal; another role is refused before any write happens.
- The author is the authenticated user. No owner or author identifier may be supplied by the request.
- A new appeal starts as `NEW`, with no owner, no outcome and no `closedAt`.
- The request carries a title and a description; both are required, must not be blank after trimming, and have a maximum length.
- The response describes the created appeal and does not expose internal ownership or outcome state.

## Acceptance criteria

- With a client session, `POST /appeals` creates exactly one row whose `clientId` is the session user, and answers `201`.
- No session returns `401`; a non-client role returns `403` and creates no row.
- Missing, non-string, whitespace-only or overlong `title`/`description` return `400` and create no row.
- Extra body fields such as `clientId`, `ownerId` or `status` have no effect on the stored row.
- The response contains the created appeal's own fields (identifier, status, title, description, creation time) and no internal ownership or outcome fields.
- `npm run build` passes and `npm test` stays green.

## Primary skill

Creating a record whose author is taken from the trusted session context, not from the request body (new application of `authorization`, target `UNDERSTAND`).

## Secondary skills

- `http-input-validation` consolidation: required text fields and trimming, following the project's existing close-flow DTO.

## Readiness

- Existing: the appeals controller/service/repository path, `AuthService.getCurrentUser` for the trusted actor, the `CloseAppealDto` trim pattern, and the `Appeal` model.
- Missing when the work started: an agreed contract, a role decision and any verification of the new path.

## Intentionally excluded

- Creating an appeal on behalf of another client, attaching files, editing or deleting appeals, notifying operators, and any frontend work.

## Risks

- Taking the author from the request body would let any client file an appeal in someone else's name; the invariant is that the author is the session user and the body can never set it.
- Omitting the role check lets an operator become the `client` of an appeal, corrupting the client relation and the ownership model that the close flow depends on.
- Returning the raw stored row makes the public response shape follow the database schema, so any later column is disclosed automatically.

## Validation and review

- Observed: `npm run build` passes and `npm test` stays green (appeals suite only) after the change.
- Observed HTTP matrix, run with two temporary sessions (one client, one operator) and cleaned up afterwards (appeals 4 → 4, sessions 22 → 22, verified):
  - no session → `401`; operator session → `403` **and no row created** (appeal count unchanged).
  - client session with a valid body → `201`; the stored row was `clientId = 1` (the session user), `NEW`, with null owner, outcome and `closedAt`.
  - the response body contained only `id`, `status`, `title`, `description`, `createdAt` — no `clientId`, `ownerId` or `outcome`.
  - whitespace-only `title` → `400 {"message":["title should not be empty"]}`; a 201-character title → `400`; a non-string title → `400`.
  - a body that also carried `clientId`, `ownerId` and `status: CLOSED` was accepted as a valid request but stored with the session author, `NEW` status and no owner — the body cannot choose them.
- Divergence found by observation (fixed 2026-10-03): a valid but padded title was stored with its surrounding spaces. Validation sees the trimmed copy, so whitespace-only input is rejected, but `transform: false` hands the handler the original object, so `@Transform(trim)` never reaches storage — measured `title = "[   padded title   ]"` in the row and in the response. The close flow uses `transform: true` and does store the trimmed value, so the two DTOs currently behave differently.
- Observed after the fix: the create handler now uses `transform: true` like the close flow, and a padded-but-valid body is stored trimmed — `title = "[padded title]"` in the row and in the response, checked with one temporary session and one row that was removed afterwards (appeals 4 → 4).
- Acceptance coverage: corrected on 2026-10-03. An earlier line here claimed every criterion was observed; the independent reviewer showed that was inaccurate, because the `description` cases and the missing-`title` case had never been exercised, and neither had an invalid-cookie `401`. The cases were then run:
  - unknown cookie value → `401`; an expired session (idle 31 minutes) → `401`.
  - valid create → `201`, and the appeal count moved by exactly one (4 → 5), which closes the indirect "exactly one row" evidence.
  - `title` missing → `400`; `description` missing → `400`; `description` non-string → `400`; `description` whitespace-only → `400 {"message":["description should not be empty"]}`; `description` of 201 characters → `400`.
  - invalid input added no row (count stayed at 5), and the run restored appeals to 4 and sessions to 22.
- Review verdict (independent, separate chat): PASS with no blocking findings. The reviewer confirmed the role check precedes the repository call, that `clientId` comes from the trusted session, that the body cannot set `clientId`/`ownerId`/`status`, that the projection hides the raw row, and that the trimming now reaches storage. It also corrected the inaccurate coverage claim above.
- Reviewer suggestions (non-blocking, not applied): use `!==` instead of `!=` at `appeals.service.ts:103`; give the role rejection a message; type the parameter as `UserRole` rather than `string`; consider whether `description` should share the `title` limit of 200 characters when the close flow allows an outcome of 2000; consider `whitelist: true` as defence in depth.
- Understanding check: satisfied by reuse rather than a new question. The author-from-session decision was the learner's own and is proven by the injection case, where a body carrying `clientId`, `ownerId` and `status` was stored under the session author as `NEW` with no owner. The role check needed teaching (`403` rather than `401`, and the `throw` form), so the ledger records it as assisted.
- Actual time: only the 15 min the learner reported for the implementation are recorded; the fix, verification and review time in the same session was not reported and is left unrecorded rather than reconstructed.
- Automated coverage: none added — consistent with the learner's recorded preference; the behaviour is covered by the runtime matrix instead, and the gap is listed as remaining work.
- Review format: to be decided with the final changed set; the endpoint creates protected product data from public input, which `docs/team/code-review.md` treats as an access-boundary candidate.
