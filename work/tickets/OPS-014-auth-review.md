## Findings

### A1 — BLOCKER: logout passes an unchecked cookie into a Prisma filter

Locations at review: `apps/api/src/auth/auth.controller.ts:55–57`, `apps/api/src/auth/auth.service.ts:63`.

The cookie value is annotated `string | undefined` but not checked at runtime. Installed cookie-parser decodes JSON cookies into objects. A truthy object reaches `session.deleteMany({ where: { id: sessionId } })`; Prisma permits an object StringFilter at `id` (generated `models/Session.ts:207`, `commonInputTypes.ts:28–40`). A filter equivalent to `not: ''` matches the nonempty UUID identifiers generated by this application. Public logout can therefore potentially delete other users' sessions rather than only the presented identifier.

This is a pre-existing input-validation risk, not introduced by the new guard. The parser behavior and dangerous filter-shaped input are confirmed; actual database deletion/HTTP exploitation was not executed. Required property: only a verified nonempty string may reach the session-id query. Invalid cookie values should behave like an absent cookie, still clear the cookie and preserve idempotent `204`. Verify this case without using production session data.

### A2 — Remaining implementation: two handlers still re-identify the caller

Locations: `apps/api/src/appeals/appeals.controller.ts:55–57`, `:76–78`; `apps/api/src/auth/session.guard.ts:37–38`.

Assign-owner and close repeat the session lookup and activity update already performed by the guard. That doubles these database operations and can use a different caller/session snapshot. Finish the agreed migration to the prepared caller context, preserving role/permission checks and their order in AppealsService. This was known unfinished work, not a new folder-design defect. `/auth/me` and appeal creation already use the decorator in source.

### A3 — IMPROVEMENT: an explicit caller contract can reduce implementation coupling

Location: `apps/api/src/auth/session.types.ts:2–4`.

The inferred `Awaited<ReturnType<...>>` is valid and avoids manually mismatched types. Its trade-off is that the shared caller contract changes automatically with the service's projection. Consider an explicit small AuthenticatedUser contract and an explicit return type on getCurrentUser if stabilizing that boundary is chosen. Keep transport/request details distinguishable. This is optional, not a present data leak or runtime circular dependency, and does not require a new file per type. The current form was mentor-recommended and is not a learner defect.

### A4 — IMPROVEMENT: narrow module exposure after migration

Locations: `apps/api/src/appeals/appeals.module.ts:5–8`, `apps/api/src/auth/auth.module.ts:14`, `apps/api/src/auth/auth.service.ts:66,73`.

Once both remaining handlers stop injecting AuthService and a search confirms no other consumers, remove that dependency from AppealsController; then the AppealsModule import of AuthModule and AuthService export can be removed. Root AppModule must keep AuthModule for global guard registration. Plain imports of a decorator/type do not themselves require a Nest module import. Helpers findUserByEmail/createSession are currently internal-only and can have private visibility. No extra repository or provider is necessary for this change.

The modest grouping collects controller-facing decorators and session lifecycle helpers, while keeping the main HTTP flow visible near module/controller/service. It adds one directory level and longer imports; flat placement is also valid. This responds to the learner's concrete navigation difficulty, not a Nest directory requirement. Folder movement is optional maintainability work, not a correctness finding.

Do not add SessionModule, PasswordService, login/logout-specific services, auth repositories or a folder for every suffix without a concrete new boundary. AuthService is currently short and cohesive enough for one provider. Preserve API paths, projections, error bodies, session timeouts, permission checks and public login/logout through any moves; compile and recheck affected HTTP flows afterward. Keep fixes and mechanical moves separate so regressions can be traced.

## Documentation and judgment

- [Nest 11 Modules](https://docs.nestjs.com/v11/modules): feature cohesion and provider encapsulation/exports. Does not prescribe the proposed directory tree.
- [Nest 11 Guards](https://docs.nestjs.com/v11/guards): APP_GUARD registration inside a module is global and supports dependency injection. Installed scanner/application-config behavior checked as well.
- [Nest Custom decorators](https://docs.nestjs.com/custom-decorators): extracting request.user through a parameter decorator is supported; callback API checked against installed Nest 11 declarations.
- [Nest Providers](https://docs.nestjs.com/providers): DI mechanisms, not a mandate to turn every helper into an injectable service.

Some current Nest pages describe newer authentication packages. No package migration or switch to those examples is justified by this review. Framework mechanics, tutorial choices and local recommendations are distinct.
