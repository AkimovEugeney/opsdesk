## Business value

A signed-in customer can follow the progress and outcome of their own requests without seeing another customer's information. Operators keep the existing shared queue for their work.

## Context

- OPS-014 is Done and pushed: authentication already protects both appeal read endpoints, identifies the caller and provides the current role. Authentication does not yet limit which customer's appeals are returned.
- Current list returns the shared active queue; detail returns any matching appeal. Existing stored appeals already identify their customer and optional assigned operator.
- The 2026-10-20 draft is now refined against the actual API. Anonymous access was closed in OPS-014, not left for this ticket. Existing title search must remain; the earlier draft's "no filters" means no additional filtering features, not removal of search.

## Visible requirements

- Keep `GET /appeals` and `GET /appeals/:id`; backend API only.
- A signed-in CLIENT sees only appeals they created, including NEW, IN_PROGRESS and CLOSED, newest first by creation time. Equal creation times have a stable order, with the larger id first.
- Customer list entries include id, title, status, creation date and outcome (null when absent). Their card includes description, closing date and the assigned operator's name (null when absent). A closed legacy appeal without an outcome remains readable and returns null for outcome.
- A CLIENT cannot read another customer's appeal through either list, title search or direct id. For a client's direct read, another customer's id and a nonexistent valid id both return 404 with the same neutral error body, without revealing ownership or existence.
- An OPERATOR keeps the existing list of NEW/IN_PROGRESS appeals and its existing ordering, and can open any appeal, including CLOSED. CAN_MANAGE_APPEALS does not affect read access. Preserve existing operator response fields and error behavior except the missing-id message: on 2026-10-22 the learner explicitly accepted the shared neutral 404 body with message "Appeal not found" for both roles.
- Existing case-insensitive literal title search applies within the caller's permitted list. Empty or whitespace-only search means no title restriction; `%`, `_` and backslash keep their existing literal-search meaning. An empty permitted/search result is `200` with `[]`.
- Without a valid session, both endpoints return 401 as in OPS-014. Existing invalid-id rejection remains 400 for authenticated callers.
- Creation, owner assignment, closing, authentication and logout keep their current behavior. No frontend, pagination, new roles or additional search/filter features.

## Acceptance criteria

- With two customers' active and closed fixtures, each customer receives only their own items in the required order, with the required outcome/card data.
- Their own active and closed detail requests return 200; another customer's known id and a missing valid id produce the same neutral 404 response.
- A title match that exists only among another customer's appeals never appears in results. Empty permitted results and missing operator/outcome values behave as specified.
- Operators with and without CAN_MANAGE_APPEALS retain active-queue access and can open any customer's active or closed appeal; queue ordering and existing response fields remain.
- Missing/invalid sessions return 401; invalid id forms/ranges remain 400 when authenticated. Existing write/role behavior does not regress.
- Build and relevant tests pass; the access matrix is verified through actual HTTP requests. Independent Code Review has no open BLOCKER.

## Readiness and risks

- Existing authentication, role, ownership data, read endpoints and local PostgreSQL are sufficient to start design; no missing product prerequisite has been identified.
- Risk: customer A guesses customer B's id or searches for a known title and receives B's data or learns that the record exists. Invariant: customer-visible lists and cards contain only their own appeals, and denial does not reveal another customer's record. Verify with two distinct customers and known foreign/missing ids.
- Risk: customer list changes accidentally alter the operator queue or drop title-search behavior. Verify both roles and active/closed fixtures before acceptance.
- Access-boundary Design Review is required before implementation; independent Code Review after. A short proposal is enough, with no opening quiz or prescribed technical solution.
