## Business value

Customers and operators can enter OpsDesk through the browser instead of manually obtaining session cookies. This prerequisite unlocks the deferred authenticated queue in OPS-011.

## Context and readiness

- Existing web app uses Next.js 16 App Router, React 19, TypeScript and SCSS Modules; current home is a static placeholder.
- API login, current-user and logout endpoints already exist and have OPS-014 validation evidence. Caller-specific appeal reads were completed in OPS-015.
- Browser session integration is missing. API currently has no CORS configuration, web has no API proxy configuration, and cookie secure behavior must be compatible with the chosen local development URLs. These are disclosed integration decisions, not hidden learner prerequisites. Existing backend authentication guarantees must be retained.
- OPS-011 remains deferred until this screen exists; its old public-queue draft requires refinement against today's authenticated API before resumption.

## Visible requirements

- A visitor sees an email/password sign-in form with Russian text, accessible labels and keyboard submission. Password characters are masked.
- Valid credentials for either CLIENT or OPERATOR open a minimal signed-in screen showing the actual user's name and role. This ticket does not display appeals.
- On initial opening/refresh, resolve the current session before showing the final signed-in or signed-out screen. A valid session survives page refresh; no saved password or readable session token is introduced.
- Invalid credentials show a neutral Russian error without disclosing whether an email exists; the visitor can correct the input and retry.
- Missing required fields are explained to the visitor. During session checking or form submission, show progress and prevent accidental repeated submission.
- API/network failure is visibly different from invalid credentials or being signed out, and offers retry. Do not present an unavailable API as an empty successful signed-in screen. Do not expose raw backend diagnostics or secrets in the UI.
- The signed-in screen has a sign-out action. Successful logout returns to the sign-in form and a refresh remains signed out. If logout fails, show an error and allow retry rather than claiming confirmed logout.
- An expired/invalid session returns to sign-in when session status is checked. No background polling requirement.
- Preserve cookie-based authentication and existing API authorization. Credentials must not be recorded in logs or persisted in browser storage. Pending UI requests must not produce stale state after leaving the relevant screen.
- Scope: existing-account login/current-session/logout only; no registration, recovery, social login, appeal list/card/actions, visual design system or unrelated refactoring.

## Acceptance criteria

- Real browser login works for a client and an operator, with correct name/role and no exposure of another user's state after switching accounts.
- Refresh restores a valid signed-in session; an absent/expired session resolves to the sign-in form without protected data.
- Wrong credentials, missing fields, slow responses and unavailable API produce the stated distinct user-visible states and permit recovery.
- Successful logout ends the supplied session; refresh stays signed out. Failed logout does not falsely claim success.
- Russian, labelled, keyboard-operable form; no password/session token persistence or secret logging introduced.
- Web build and lint pass. If API integration changes, its build and affected checks pass. Browser behavior and session integration are actually observed; independent review has no open BLOCKER.

## Risks

- Browser requests may succeed in a manual API client but fail to establish or restore a browser session because the selected origin/cookie boundary is inconsistent. Verify actual login plus refresh/logout in a browser.
- A failed session check may be misrepresented as invalid credentials or confirmed logout; stale previous-user state may remain visible after switching identity. Verify outage, retry and account-switch scenarios.
- Changes to origin/cookie forwarding may broaden access unintentionally. Review the actual chosen trust boundary before implementation and independently before acceptance; do not relax backend checks to make the UI work.
