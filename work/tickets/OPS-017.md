## Business value

Customers currently see status and final outcome but no explanation of ongoing work. Operators need to publish customer-visible progress updates that remain available with the appeal. This follows the approved customer-request workflow and product rule that material progress is recorded.

## Context and readiness

- Existing NestJS/PostgreSQL API identifies authenticated callers and enforces customer-owned appeal reads; operator role and assigned owner already exist.
- No progress-update storage or API exists yet. A persistent relation/data change is required; this is the primary new mechanism. Learner proposes it before implementation, including treatment of existing appeal data.
- Frontend is explicitly deferred by the learner on 2026-10-22. This ticket is API-only.

## Visible requirements

- An authenticated OPERATOR can publish a text update for an existing appeal. Any operator may do so, independently of assignment and CAN_MANAGE_APPEALS. Updates are allowed for active and closed appeals (for example a post-resolution clarification).
- The update records its actual authenticated author and server creation time. A request cannot choose another author or creation time.
- Text is required, trimmed at the edges, and must contain 1–2000 characters after trimming. Missing, nonstring, blank or oversized text returns 400 without creating an update. A simple length rule is sufficient; no rich text.
- These updates are explicitly customer-visible. There are no internal/private notes in this ticket.
- A CLIENT can read updates only for an appeal they created, including a closed appeal. An OPERATOR can read updates for any appeal.
- Each returned update includes its id, text, author name and creation time. Return oldest first, with ascending id for equal creation times. A readable appeal with no updates returns 200 and an empty array.
- For a CLIENT reading updates, a foreign appeal and a nonexistent valid appeal id return the same neutral 404 body. Do not return an empty success for a missing appeal.
- CLIENT cannot publish updates and receives 403 for a validly shaped request before parent existence is disclosed. OPERATOR publishing/reading for a missing valid parent gets 404.
- Missing/invalid session returns 401 before parameter/body validation. Invalid appeal-id forms/ranges return 400 for authenticated callers. Existing read/create/assignment/close/auth behavior is preserved.
- Publishing is append-only: no edit/delete, attachments, notifications, pagination, client replies, internal notes or appeal-status change. Repeated submissions are distinct updates; retry deduplication is not promised.

## Acceptance criteria

- An operator with and without management permission can publish an update under their own identity and read it back; no ownership assignment is required.
- A customer sees updates on their own active/closed appeals, never another customer's; foreign and missing parent responses are identical neutral 404s.
- Empty permitted history returns 200 []; author name/text/date/id and deterministic oldest-first ordering are correct.
- Input boundary cases and forged author/time fields cannot create invalid or misattributed updates. Missing session, forbidden customer publishing and absent/invalid parent behave as specified.
- Existing appeals survive the data change and remain readable. Application restart does not lose saved updates. Relevant API build/checks pass; actual HTTP behavior is verified and required independent review has no open BLOCKER.
