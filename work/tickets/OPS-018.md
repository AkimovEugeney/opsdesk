## Business value

An operator with appeal-management permission distributes incoming work. The active queue shows individual appeals, but there is no compact view of how many active appeals each operator owns or how much work remains unassigned. A workload summary will support assignment decisions without counting the queue manually.

## Context and readiness

- Current product already stores operator identity, appeal ownership and NEW/IN_PROGRESS/CLOSED states. Assignment and closing are implemented; authentication exposes role and CAN_MANAGE_APPEALS.
- Existing active appeal reads have customer/operator access boundaries. No workload summary currently exists.
- API-only: frontend OPS-016/011 remains deferred. No new role, schema change or external service is required by the business scope.

## Visible requirements

- An authenticated OPERATOR with CAN_MANAGE_APPEALS can request the workload summary. A CLIENT or OPERATOR without that permission receives 403. Missing, invalid or expired session receives 401.
- The summary includes every current operator, including operators with no active appeals and operators without management permission. It contains each operator's id, name and active owned appeal count. Names need not be unique; operators must remain distinguishable by id.
- Active means NEW or IN_PROGRESS. CLOSED appeals are excluded. Count appeals, not progress updates; multiple updates do not increase workload.
- Also return the count of active appeals with no owner and the total number of active appeals. Within one response the per-operator counts plus the unassigned count equal the total. Valid product data has an operator as any assigned owner.
- List operators in ascending id order. Counts are nonnegative integers. Do not expose customer details, appeal text, user email, password data, sessions or permissions.
- With no appeals, return success with zero counts and the existing operators listed. With no operators and no appeals, return success with an empty operator list and zero totals.
- After a successful assignment or reassignment, a subsequent summary reflects the new distribution. After successful closure, the appeal no longer contributes. Historical updates and closed appeal outcomes are retained.
- This is a read operation: do not change appeals, ownership or updates. Existing normal session-activity bookkeeping is allowed. Existing appeal/auth behavior is preserved.
- No new filtering, pagination, dashboards, historical analytics, SLA targets, notification delivery or per-operator appeal listing in this ticket. No consistency promise across separate requests during simultaneous changes is introduced.

## Acceptance criteria

- Manager sees exact expected per-operator, unassigned and total counts using a nonempty mixture of NEW, IN_PROGRESS and CLOSED appeals, at least two operators and an operator with zero active appeals.
- A NEW appeal contributes; a CLOSED appeal does not. Adding several progress updates to one appeal leaves workload unchanged.
- Separate operators with the same display name remain separate entries; ordering by id is deterministic. Returned fields are limited to the agreed safe summary.
- Assigning an unassigned appeal, reassigning an active appeal and closing it produce the expected subsequent count changes without double counting.
- Empty-data responses and role/session denials follow the visible requirements. Denied requests disclose no workload data.
- Existing behavior remains valid, relevant checks pass and actual HTTP observations plus the required independent review support completion.

## Risks and review

- An unauthorized client or operator obtains team workload and identities: protected operational data is disclosed. Access must be checked with all existing role/permission variants and invalid sessions; independent review required.
- Counting by display name or progress records could merge different operators or multiply their load: lead assigns work based on false numbers. Check duplicate names, multiple updates, zero-load operators and exact totals against known fixtures.
- Counts could drift from ownership/status or expose sensitive fields: verify before/after actual assignment, reassignment and closing, and inspect the public response.
- Public contract and permission boundary require a short Design Review of the learner's proposal before implementation. Learner chooses the API shape; no route name or technical solution is supplied by this ticket.
