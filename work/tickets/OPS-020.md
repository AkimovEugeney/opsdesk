## Business value and context

A customer looking for a previous resolution currently has to scan a list that mixes open and completed appeals. Operators also need to find completed appeals and read their outcomes.

## Requirements and acceptance criteria

- GET /appeals?filter=closed returns completed appeals with their recorded outcomes. A signed-in customer sees only their own appeals. A signed-in operator sees all completed appeals.
- Completed operator results are ordered by createdAt descending, then id descending. They retain the operator search semantics and existing page response format.
- The completed-only view retains the customer list's existing search semantics, order and pagination contract. With closed and open appeals interleaved, equal creation timestamps, and a matching closed appeal belonging to another customer, walking the pages returns exactly the expected IDs in order, once each, with no foreign records. Combine search with pagination in this check.
- With no matches, return an empty page with no continuation. The terminal non-empty page also has no continuation.
- Requests without the new option retain existing behavior for both roles. Any supplied filter value other than closed returns 400 for an authenticated customer or operator. A request without a session receives 401.
- Verify both roles with search and multi-page walks, equal creation timestamps, empty and terminal pages. Operator results include completed appeals across customers and exclude active appeals.
- Backend only. No schema or data changes. See [requirements log](OPS-020-requirements-log.md).
